# CV studio (suite `cv-studio`)

Per-account career workspace: one or more CV projects (separate CVs, see "Projects"), each with a bilingual (PL/EN) master CV profile, saved job offers (link or pasted text),
per-job CV versions ("variants"), tracked applications, project-showcase evidence. The widget agent drives it two ways: the live UI tools
(fill_field/click on the tabs) and deterministic `knife_cv_*` tools (also on MCP). **Tools gather evidence and apply deterministic checks; the
model (the widget's own provider) writes the prose. No CV code calls an LLM.**

The engines were ported from a standalone Python prototype that no longer exists (deleted 2026-10-09; its git history is in the bundle `~/work/_backups/cv-helper-all-20261009.bundle`). The TypeScript tests in `tests/cv_*.test.mjs` are the spec now.
Never commit personal CV data; fixtures are synthetic. Real data lives in `$KNIFE_DATA_DIR/cv/<account>.json` (mode 600) + `.snapshots/`.

## Contract (stable: lanes build against this)
- `src/lib/cv/schema.ts` — zod: `Profile` (all text `{pl,en}`, list items have `id`), `Variant` (overlay, `null` = keep all), `Job`, `Application`, `CvData{version,revision,profile,variants,jobs,applications}`.
- `src/lib/cv/ops.ts` — `applyOps(profile, ops)` atomic id-path edits (`/experience/id=x/bullets/id=y/text/en`, append `.../-`) returning `CvChange{op,path,before,after}`; `readPath`, `missingTranslations`.
- `src/lib/cv/variant.ts` — `resolveVariant(master, variant) -> Profile` (what renderers consume), `danglingIds`.
- `src/lib/cv/collections.ts` — pure `upsertJob/removeJob/upsertVariant/removeVariant/upsertApplication/removeApplication/dueApplications`, `slugify`, `uniqueId`, `todayIso`.
- `src/lib/cv/store.ts` (server only) — `loadCv/saveCv/mutateCv/undoCv`; every save bumps `revision` and snapshots the previous state (40 kept).
- `src/lib/cv/import.ts` — `importProfile` (refuses to overwrite unless `overwrite`).
- Routes (all via `authenticate`; mutating ones pass the Origin guard): `GET|POST|DELETE /api/cv/photo` (see "Photo and document layouts"), `POST /api/cv/export {variantId, lang, theme: ats|modern|sidebar|elegant, photo?, photoShape?}`, `GET /api/cv[?revision=N]` (`{changed:false}` when unchanged: cheap polling), `POST /api/cv/patch {ops}`, `POST /api/cv/undo`, `POST /api/cv/import {profile,overwrite?}`, `POST|DELETE /api/cv/jobs|variants|applications` (`{job|variant|application}` / `?id=`). Errors are real 4xx with a reason (422 invalid, 404 unknown id, 409 conflict).
- Tools: `src/lib/mcp/tools-cv.ts` (core: get/patch/missing/import/undo + job/variant/application CRUD + `app_due`); lane files `tools-cv-text.ts`, `tools-cv-jobs.ts`, `tools-cv-showcase.ts` export `CV_*_TOOLS` arrays that `tools-cv.ts` already includes. Tool prefix `knife_cv_` is the on-demand tool group `cv` (`tool-groups.ts`, preloaded on `/tools/cv-studio`). `KnifeToolContext{accountId}` is passed by `/api/agent/tool`; MCP uses the default account.
- Registry: suite `cv-studio`, tabs `profile`, `jobs`, `variants`, `applications`, `showcase`, `website` → components `cv-*` in `src/tools/registry-client.tsx`, all wrapped by `src/tools/cv/framed.tsx` (the project bar + "How this works" above every tab). The retired `site-studio` slug redirects to `?tab=website` (its old tab becomes `&step=`).

## Rules for CV code
- Truthfulness: never fabricate employers, dates, numbers or achievements; a rewrite keeps every fact; tool descriptions say so.
- Pure logic in `src/lib/cv/**` (no node/DOM APIs) unless the file is explicitly server-only; unit-test it with `node --test` (`tests/cv_*.test.mjs`, loader `tests/ts-resolve.mjs`; `@/` aliases do not resolve there, so keep pure files on relative imports).
- Hydration: no bare `toLocaleString`/`Intl.*(undefined)`; format dates/numbers with pinned locale or ISO.
- Server fetches of user-supplied URLs need an SSRF guard (block loopback/private/link-local/CGNAT incl. Tailscale, re-check every redirect, DNS-resolve first, size + time caps, http(s) only).
- Child processes: argv arrays only (`execFile`), timeouts, output caps, allow-listed roots; never read secret-like files.

## Photo and document layouts (2026-10-12)
- Photo: one JPEG per account at `$KNIFE_DATA_DIR/cv/<account>.photo.jpg` (mode 600), deliberately outside the CV JSON (not polled, not snapshotted, never handed to the model). `src/lib/cv/photo-store.ts` (server only); `GET /api/cv/photo` (image, 404 none), `GET ?meta=1` -> `{photo:{bytes,updatedAt}|null}`, `POST {dataUrl}` (JPEG data URL only, ≤1.5 MB, 422 otherwise), `DELETE`. The browser (`src/tools/cv/photo-crop.ts`) decodes the pick, crops a square (zoom + drag/sliders), scales to ≤800 px and re-encodes as JPEG, so EXIF/GPS never reach the server. Profile tab: Photo panel (`PhotoPanel.tsx`); `usePhoto.ts` shares the state between tabs. Undo does not cover the photo.
- Layouts (`src/lib/cv/render/layout.ts`, ids = the stored pref and the export `theme`): `ats` (plain, never a photo), `modern` (photo beside the name), `sidebar` (two columns: photo, contact, skills, languages, education left), `elegant` (centred serif header, photo above the name). Photo switch (Show/Hide) and shape (Round/Square) are per-tab prefs (`DocumentOptions.tsx`), not stored per version. `CvDocument` renders all four; `cv_docx.py` mirrors them (ATS and photo-less Modern/Elegant stay one table-free flow; Sidebar = one shaded two-column table; Modern + photo = one name|photo table; round photo = Pillow PNG with alpha). Tests: `tests/cv_photo.test.mjs`, `tests/cv_docx_test.py`, `tests/cv_photo_e2e.py`.
- Audit hints are shown to the user ("Tip:") and read by the model: phrase them for both (no "ask the user"), and keep the no-fabrication rule in them.

## Applications and "what is still open" (2026-10-09)
- `Application.appliedOn` (YYYY-MM-DD): the day it was sent. Stamped automatically when the status becomes `applied` (a stated date wins, for backfilling); never moved by later status changes; `null` for wishlist or when the stage was entered later without a date (we do not guess). Status history keeps every dated transition.
- `summarizeApplication(app, today)` (pure, `collections.ts`) derives `daysSinceApplied`, `open` (wishlist/applied/screening/interview), `inProgress` (applied/screening/interview), `overdue`, `closedOn`, `lastUpdate`. Tools and UI use it; nothing is stored twice.
- Tools: `knife_cv_app_list {status?, open?, sort?}` (counts + sorted pipeline, oldest-applied first), `knife_cv_app_due`, `knife_cv_app_save` (`appliedOn`), `knife_cv_job_list` (each offer carries its `application {id,status,appliedOn}` or null). UI: Applications cards show `Applied <date> · N days ago`, the drawer has an "Applied on" field, the offer list badges show status + date.

## The assistant works with it from every page
The widget's system prompt teaches the `cv` tool group (`system-prompt.ts`); on any page the model calls `load_tools {group:"cv"}` once and then uses `knife_cv_*` (the group is preloaded on `/tools/cv-studio`, absent elsewhere to keep the request prefix small). Proven by `tests/cv_agent_anywhere_e2e.py`. `open_tool {slug:"cv-studio", tab}` shows the user the result.

## Tailoring for an offer (2026-10-14)
Goal: dozens of applications, each with a version fitted to the offer and to ATS parsers, Polish by default, nothing invented.
- Data (all defaults, old files load unchanged): `pinned` on roles, bullets, projects, skill groups, own sections and their items (priority: always kept, listed first); `Profile.customSections` (user-defined sections: title, items with title/text/url/date), `Profile.sectionOrder` (null = standard; keys `summary|experience|projects|skills|education|languages|extras|custom:<id>`), `Profile.guidance` (tailoring notes, never printed); `Project.source` (`github:owner/name`). `Variant.lang` and `Application.lang` default to `pl`; `Variant.customSectionIds`, `Variant.sectionOrder`, `Variant.rewrites` (`[{path, text:{pl,en}}]`, per-version wording; paths limited by `REWRITE_PATH`: bullet texts, project summaries, experience notes, own item texts; an empty side keeps the master text). `Job`: `skills[{name, level, required}]`, `seniority`, `workplace`, `salary`, `languages`, `applyUrl`, `companyUrl`, `companyText` (company website text, context only), `notes` (the user's own notes, read when tailoring), `source` adds `justjoin`.
- Rendering: `buildCvView` returns `order` (non-empty sections, print order) and `custom`; the HTML document, the text preview and `cv_docx.py` all iterate `order` (Sidebar keeps skills/languages/education in the left column in that order). `resolveVariant` applies rewrites first (they address master ids), then the selection, own sections and order.
- Offers: `jobs/justjoin.ts` reads a justjoin.it offer link through the board's own JSON (`/api/candidate-api/offers/<slug>`, the page is a JS shell whose JSON-LD glues lists together) via the same SSRF-guarded download; if the API fails the page is parsed as before. `jobs/sections.ts` takes requirement / nice-to-have lines from the posting's own headings (PL/EN, emoji and `*`/`1.` bullets, an unknown `Heading:` ends a section) for every source incl. pasted text; on 20 live justjoin.it offers (2026-10-14) all 20 gave requirement lines. `jobForMatching` adds the board's skills to the requirement lines they are not part of and the user's notes to the prose. The company website is read once (`fetchPageText`, 8k chars) when given; failure is a `companyNote`, never a failed save. `POST /api/cv/jobs/company {jobId, url?}` re-reads it.
- Tailoring: `suggestVariant` keeps pinned items first (pinned roles keep every bullet) and prints projects before experience when a project is pinned or projects carry more of the offer's evidence, unless the user fixed `sectionOrder`. `priorities.ts` `priorityWarnings` (pinned left out, pinned projects not first, projects after experience with a pinned project, roles reordered against the profile) is returned by `knife_cv_variant_create` and shown as ATS checks.
- Fact guard for rewrites (`text/guard.ts` `rewriteWarnings`): facts dropped from the master text, facts ADDED that the profile contains nowhere (numbers, names, urls, versions), and claim-strengthening words the master text does not make (`addedClaims`: production, enterprise, scale, seniority, leadership, architecture, sole ownership, volume). Warns, never blocks; the UI shows the warning on the row.
- ATS check (`jobs/ats.ts`, `POST /api/cv/variants/ats`, `knife_cv_ats_check`): reads what the version PRINTS in its language (tags and the other language do not count). Keywords = dictionary technologies + the board's skills (literal phrases); generic words from requirement sentences are not keywords. Status present / dropped (in the profile, left out) / missing (a gap, never to add); offer spellings the version writes differently; structural checks (contact, headline vs offer title, summary length, translations, dates, length, RODO clause in PL, languages asked, years asked vs dated roles, priorities). Output splits `fixable` from `gaps`; the tool says "nothing left to fix, do not run again" when `fixable` is empty (the first real-model run looped 13 times on unfixable gaps).
- Projects from GitHub (`showcase/draft.ts`, `POST /api/cv/showcase/project`, `knife_cv_project_from_github`): name, link, main languages (>= 5% of code), topics and dependency names that are known technologies, the repo description (EN only; PL left for a translation). An existing project linked to the repo only merges technologies; the user's wording is kept.
- Tools: `tools-cv-tailor.ts` adds `knife_cv_tailor_context` (offer + notes + company excerpt + guidance + pinned + suggestion in one call), `knife_cv_variant_rewrite`, `knife_cv_ats_check`, `knife_cv_job_company`, `knife_cv_project_from_github`; `knife_cv_job_fetch` takes `companyUrl` and `notes`; `knife_cv_job_save` keeps a saved offer's `source` on update.
- UI: Job offers (company website + notes on the form, "From the job board" facts, notes and website on the offer, "Tailor with the assistant" sends a prompt with the jobId and language, "Quick version (no rewording)" is the old deterministic suggestion); Profile ("Tailoring priorities": notes, pinned count, section order; ☆ pin on roles/bullets/projects/skill groups/own sections; "Your own sections"; "Add from GitHub"); CV versions (ATS check panel, "Wording for this version" with Reword/Restore and the guard's warnings, section order, own sections in "What goes in").
- Verified 2026-10-14: unit 578 (`tests/cv_tailor.test.mjs` 32), `cv_docx` 7/7, `f_cv_studio` 52/52 (new: offer notes/website, board facts, tailor prompt, pins/notes/own section/order, GitHub error, ATS panel, rewording guard + Restore, own sections in the preview); real model (`knife-test` gateway agent) three runs on a copy of the real profile + a live justjoin.it offer: run 1 found the ATS loop and the ignored priorities, run 3 = 9 rounds, 251k tokens, 107 s, pinned project first, projects before experience, headline + summary written, 8 truthful rewrites, ATS once, gaps reported, nothing invented; DOCX of that version read back with python-docx.

## Projects (2026-10-27)
One account holds several independent CVs ("CV projects": other people, or separate CVs of one person). Each has its own CV data and undo snapshots, photo and website connection; the GitHub App installations stay account-wide.
- Storage (`src/lib/cv/projects.ts`): `cv/<account>.projects.json` = `{version:1, active, projects[{id,name,createdAt}]}`; absent = one project `main`. Project `main` IS the pre-project layout (`cv/<account>.json`, `.snapshots/`, `.photo.jpg`, `site/<account>.json`), so old accounts need no migration and nothing moves; other projects use `cv/<account>.p-<id>.{json,snapshots,photo.jpg,site.json}`. Everything is under `cv/<account>.` (quota, rename and account deletion cover it), sealed like every account file. Max 30 projects; the last one cannot be deleted.
- Which project a call uses: the one bound for the request (`?project=` on every `/api/cv/*` and `/api/site/*` route, `bindRequestProject`; `projectId` on every `knife_cv_*` / `knife_site_*` tool, `withCvProject`, src/lib/mcp/project-scope.ts), else the account's ACTIVE project. The browser names the project it shows on every call except the polled `GET /api/cv` (`src/lib/cv/shown-project.ts`), which follows the active project, so a switch made by the assistant or another tab is followed within ~2 s and never redirects the page's edits.
- API: `GET /api/cv` also returns `project`, `active`, `projects`; `?revision=N&shown=<project>` answers `{changed:false}` only for the same project. `GET|POST|DELETE /api/cv/projects` (`create` {name, duplicateOf?} -> becomes active; duplicate copies CV + photo, never the website; `rename`; `switch`; DELETE removes CV, snapshots, photo, website).
- Tools: `knife_cv_project_list` (with the name on each CV), `knife_cv_project_create`, `knife_cv_project_switch`; deleting is UI-only.
- UI: project bar (switcher, "Manage CV projects" drawer: create empty / as a copy, open, rename, delete with confirm) and a short "How this works" on every tab. An empty project shows "Start here" (`StartHere.tsx`): use an existing CV (`CvStartUpload`: paste the text for the assistant to structure, or a JSON profile), build from scratch (a short form written with `/api/cv/import`), or an assistant interview.
- Website (`site-studio` folded in): the Website tab has steps Your website / Check it / Compare with your CV / Improve it (optional). Any user may connect a GitHub repository (App or own token; only the server's own `gh` login is admin-only) or just save the site's address (docs/WEBSITE-STUDIO.md "Without a repository").
- Tests: `tests/cv_projects.test.mjs`, `tests/site_url_only.test.mjs`, `tests/functional/cv_projects_e2e.py`.
